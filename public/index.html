01 — The problem

The sandbox protects the host. Nothing protects your data.

Agents no longer just answer prompts. They call tools, read and write files, and use credentials on their own. Docker, gVisor or Firecracker stop an agent from escaping to the kernel. They do not stop it from sending a customer record to a third-party model.

FAILURE MODE A

Leakage

There is no gate between your agents and the LLM provider. Secrets, API keys and personal data go straight through in prompts and tool results.

FAILURE MODE B

No audit trail

In healthcare, legal and finance you need a record of what the agent did: which tools, which data, in what order. API logs only show that a model was called.

sandbox → protects the host

  • ✕ crashing the host
  • ✕ reading /etc/passwd
  • ✕ unbounded RAM and CPU
  • ✕ escaping to the kernel

agentkeeper → protects the system and data

  • ✓ anonymous callers
  • ✓ calls to models or tools it may not use
  • ✓ secrets and PII leaving in a payload
  • ✓ ten thousand calls a second
  • ✓ leaving no trace

You need both. AgentKeeper does not replace your sandbox; it works with whichever one you already run.

02 — The governance pipeline

Six stages, in a fixed order, on every call.

Every request that leaves an agent passes through the same pipeline before it reaches the provider. The order is set at build time and cannot be changed in config. Any stage can deny the call, and the first denial stops it.

  1. 01 available

    Identification

    Authenticates each call to a registered agent_id using a per-agent API key or a signed JWT. Every failure returns the same generic denial, so callers cannot probe for valid IDs.

  2. 02 roadmap

    Policies

    Declarative rules in OPA/Rego: which models, tools and resources each agent may use, and when. Policies are code you can review, version and change without redeploying.

  3. 03 roadmap

    Monitoring

    Call frequency, token volume, latency and error rates per agent, with alerts on anomalous behaviour.

  4. 04 roadmap

    Filtering

    Detects secrets, API keys, personal data and prompt injection in payloads, and blocks or redacts them while the request is in flight.

  5. 05 roadmap

    Rate limiting

    Quotas per agent and per model, with burst control. A runaway loop hits a limit before it runs up your bill.

  6. 06 tracing available

    Audit

    Records who called, what they did, when, and what each stage decided. Every call is logged, whether it was allowed or denied.

  • Fails closed

    If a stage errors, the call is denied, not forwarded. A broken governance layer never turns into "allow everything".

  • Keeps your keys

    Only the gateway holds the provider key. Whatever credential the caller sends is stripped, and nothing is logged.

  • Says little to the caller

    A denied agent learns which stage refused and gets a request ID. The detailed reason goes only to operators.

  • Invisible when allowed

    Responses stream as fast as the provider sends them. An allowed call behaves exactly as if AgentKeeper weren't there.

05 — Adoption

Change one URL. Your agents keep working.

Point your agents at AgentKeeper instead of the model provider. There's no SDK to add and no agent code to change. Claude Code, opencode and any Anthropic SDK work as they are.

  1. step 1

    Run the gateway

    A single Go binary or container, in your cloud, on-prem, or next to the agent. The provider API key stays in the gateway.

  2. step 2

    Register your agents

    Give each agent its own credential. Agents never hold a real provider key, so there's nothing for them to leak.

  3. step 3

    Change the base URL

    Point the agent's base URL at the gateway. Every call and every tool call is identified and traced from that point on.

    ANTHROPIC_BASE_URL=https://gw.internal

06 — Sovereignty

Your agents, your infrastructure, your jurisdiction.

Governance should not require sending your traffic to yet another third party. AgentKeeper is designed so that you choose where the data goes, and it stays there.

deploy

Self-hosted or hosted in the EU

Run it on your own cloud or on-prem. If you prefer SaaS, it is hosted in Europe so data stays in the region.

intercept

No TLS interception

Agents route to AgentKeeper explicitly. We do not spoof DNS or decrypt traffic; that approach is a GDPR grey area and we avoid it.

standards

Open formats, no lock-in

OPA/Rego for policies, W3C baggage for sessions, versioned JSON for traces. Bring your own observability stack.

minimise

Data minimisation by default

Traces contain metadata and fingerprints, never payload content. This page itself makes no third-party requests.

07 — Why AgentKeeper

Security is the product, not the upsell.

  1. i.

    Governs actions, not only model calls

    LLM gateways control access to the model: routing, spend and rate limits. AgentKeeper also sees what the agent does with the tools, files and credentials it has been given.

  2. ii.

    Designed for compliance from the start

    Audit trails and controls are designed around healthcare, legal and financial requirements. They are part of the core, not a set of third-party plugins.

  3. iii.

    No paywall on safety

    Many tools offer a free, ungoverned base and charge for audit logs and PII controls. For a security buyer that is the wrong way round, so these are included.

What AgentKeeper is not

A multi-provider LLM router
see LiteLLM, OpenRouter
A sandbox
use Docker, gVisor, Firecracker
A firewall or service mesh
network isolation is the sandbox's job
A secret manager
keep your vault; we read env vars
A cost optimiser
we govern; we don't route

Being explicit about scope matters. A governance tool that claims to do everything is harder to audit and to trust.
